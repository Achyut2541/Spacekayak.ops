Executive Summary

Fermi Ops is well-architected at the surface — clean context separation, good component boundaries, smart workload calculations. But the auth-to-identity pipeline is broken at the core: every user who logs in sees Achyut's dashboard, because currentUser is hardcoded to 'Achyut' and never derived from the authenticated email. This is a P0 blocker that makes the entire role-based dashboard system non-functional for any real user.

Beyond that, the dashboard has structural gaps at both the manager and team-member layers — missing loading states, a duplicated "Due This Week" section, a bypassed hours-logging prompt, and stat cards with no drill-down. The Settings page is also wired wrong and will silently fail on every Basecamp sync click. These are all fixable in one tight sprint.

Critical Issues

2 P0 · 3 P1
P0 · Blocker
currentUser is hardcoded to "Achyut" — every user sees the wrong dashboard
src/contexts/AuthContext.jsx · line 12

After a successful Supabase login, currentUser is never updated to match the authenticated email. The state initialises as 'Achyut' and stays there. This means Navaneeth logs in with navaneeth@spacekayak.xyz, passes auth, and then lands on Achyut's manager dashboard with full admin access in the UI. The entire role-based split between manager view and team-member view is broken for all real users.

// AuthContext.jsx — the problem const [currentUser, setCurrentUser] = useState('Achyut'); // ← hardcoded // login() — email stored but never mapped to a name const login = async (email, password) => { const { data, error } = await supabaseAuth.signIn(email, password); // setCurrentUser is never called here localStorage.setItem('sk_auth_email', email); ... };
Fix

After login resolves, look up the email in teamMembers (or pass it through the auth payload) and call setCurrentUser(matched.name). Since DataContext loads after AuthContext, do this lookup in a useEffect inside DataProvider once dataLoaded is true, or store the email and resolve it lazily. Also fix the restore() session function the same way — it reads email from localStorage but never resolves it to a name.

P0 · Blocker
Settings page is wired to a prop that is never passed — Basecamp sync silently fails
src/components/settings/SettingsView.jsx · src/components/layout/AppShell.jsx

SettingsView receives a syncEngine prop and gates the sync button on if (!syncEngine) return. But AppShell renders <TabRouter /> which renders <SettingsView /> with no props — syncEngine is always undefined. Clicking "Sync Now" does nothing and no error is shown. Any user who tries to connect Basecamp will think it's broken with no feedback.

// SettingsView.jsx const handleSync = async () => { if (!syncEngine) return; // ← always returns, syncEngine is never provided ... }; // TabRouter in App.jsx — no prop passed case 'settings': return <SettingsView />;
Fix

Either instantiate syncEngine in DataContext and expose it via the context (cleanest), or instantiate it in App.jsx and thread it through the component tree. Also add a visible error state when syncEngine is null rather than silently swallowing the click.

P1 · High
Leadership role (Paul, Saaket) is hardcoded in DataContext but they have no email → they can never log in
src/contexts/DataContext.jsx · src/data/seed.js

Paul and Saaket are assigned 'leadership' sysRole directly in the userRoles memo inside DataContext, but they don't exist in SEED_TEAM and have no email address. canViewAllProjects grants them read-only access to all projects, but they can never actually authenticate because there is no Supabase user record for them. This role is dead code today, and if you ever want real leadership visibility, you'll need to add them as team members with proper emails.

Fix

Add Paul and Saaket to SEED_TEAM with their @spacekayak.xyz emails and sysRole: 'leadership'. Remove the hardcoded entries from the DataContext memo — roles should always come from the team member record, not from scattered constants.

P1 · High
No signup flow in the UI — new team members can't onboard themselves
src/components/auth/AuthScreen.jsx

AuthContext has a fully implemented signup() function, but AuthScreen never surfaces it. The only path in is login + forgot password. To add a new team member today, someone has to manually create a Supabase user in the dashboard AND add a row to SEED_TEAM / the DB. This creates an ops burden every time you onboard someone new. Even an invite-only flow (admin sends invite link, user sets password) would eliminate this.

Fix

Add an invite-based onboarding: admin enters email in Settings → Supabase sends magic link → user lands on a set-password screen → they're dropped into their correct dashboard. Use signup() which is already wired. The domain restriction (@spacekayak.xyz) is already enforced client-side — keep it but also enforce server-side via Supabase email templates.

P1 · High
No loading state during the 4-second Supabase boot timeout — users see a blank screen
src/contexts/DataContext.jsx · boot() function

DataContext has a dataLoaded flag that correctly starts as false and is set to true after the Supabase boot. But the app renders children immediately — AppShell, DashboardView, etc. — without checking dataLoaded. Users see the full UI shell with seed data for up to 4 seconds before real data arrives, then the view silently re-renders. If the Supabase load is slow or fails, there's no visible feedback at all.

Fix

Consume dataLoaded in AuthGate or AppShell and render a skeleton layout until it's true. The Skeleton UI component already exists in src/components/ui/Skeleton.jsx — wire it up. Also surface a toast or inline error when Supabase times out rather than silently falling back to seed data.

P1 · High
completeTask() on the dashboard bypasses the hours-logging prompt entirely
src/components/dashboard/DashboardView.jsx · completeTask()

updateTask() in DataContext returns { needsHoursLog: true } when a task is being completed without actual hours logged. TasksView correctly handles this and shows a modal. But DashboardView's completeTask() ignores the return value — it calls updateTask(taskId, { status: 'completed' }) and discards the result. This means every task completed from the dashboard skips actual hours collection, corrupting your historical estimation accuracy data.

// DashboardView — ignores the return value const completeTask = (taskId, projectId) => { updateTask(taskId, { status: 'completed' }); // returns { needsHoursLog: true } — ignored ... }; // TasksView — correctly handles it const result = updateTask(taskId, { status: 'completed' }); if (result.needsHoursLog) setLoggingHoursTask(taskId);
Fix

Mirror the TasksView pattern: capture the return value of updateTask and if needsHoursLog is true, call setLoggingHoursTask(taskId) from UIContext. The LogHoursModal is already built — it just needs to be triggered from here too.

P2 · Medium
Sidebar "Team" nav item is duplicated for admin users
src/components/layout/Sidebar.jsx · items construction

"Team" appears in the NAV_ITEMS constant AND is appended again via canEditProjects(currentUser) check. Admins see two "Team" entries in the sidebar. This is a simple logic error — the nav item array shouldn't contain "team" in the static list if it's being conditionally added.

// NAV_ITEMS already contains team... { id: 'team', icon: Users, label: 'Team', showCount: 'team' }, // ← here // ...then it gets added again: const items = [ ...NAV_ITEMS, ...(canEditProjects(currentUser) ? [{ id: 'team', ... }] : []), ];
Fix

Remove the "team" entry from NAV_ITEMS and keep only the conditional version, or flip the logic — include it in NAV_ITEMS and filter it out for non-admins.

P2 · Medium
Search bar only filters projects — tasks, people, and phases are invisible to search
src/components/dashboard/DashboardView.jsx · searchQuery filter

The global search in the header sets searchQuery in UIContext, but only DashboardView consumes it, and only to filter project names and types. Searching "Navaneeth" returns nothing. Searching "QA" returns nothing. The mental model the search bar implies — global, cross-entity search — is completely unmet by the current implementation.

Fix

Either scope the search bar clearly (rename it "Search projects…") or expand the implementation to search tasks by title/assignee and team members by name. Given you already have a tasks view and team view, a simple client-side filter function would cover 90% of use cases.

P2 · Medium
"Due This Week" in team member view duplicates what's already in "Active Tasks" above it
src/components/dashboard/DashboardView.jsx · team member return block

myThisWeek is filtered from myActiveTasks — so every task in the "Due This Week" panel was already rendered in "Active Tasks" directly above it. For most team members with <10 tasks, this creates a visually confusing double-listing with no incremental value. The section earns its place only if it shows tasks the first section doesn't — like tasks from other contexts, or tasks where someone else is primary.

Fix

Either remove "Due This Week" from the team member view and keep it as a manager-only summary, or repurpose it to show tasks not yet in the active list (status: 'backlog' but due this week). The "next week" equivalent — a planning horizon — would be more useful than repeating the same tasks.

P3 · Low
No real-time Supabase subscriptions — concurrent users will see stale data
src/contexts/DataContext.jsx

Supabase offers supabase.channel().on('postgres_changes', ...) for real-time updates. Currently, data is only fetched once on boot and then mutated locally. If Achyut marks a task delayed while Hari is viewing the same project, Hari sees nothing until they refresh. For an ops tool used concurrently by 15+ people, this is a meaningful gap — especially for the Attention Banner which is supposed to surface urgent items.

Fix (Sprint 2)

Add Supabase realtime subscriptions to projects and tasks tables in DataContext. The debounced auto-save pattern already in place will handle conflicts gracefully. This is a nice-to-have for now but becomes critical as team size grows.

What's Actually Strong

don't touch these
Things working well

Context architecture is clean. Separating Auth, Data, and UI into three discrete contexts is the right call. DataContext doesn't bleed into AuthContext, UIContext doesn't hold business logic. This is exactly how a well-structured React app should be organized.

The workload/capacity engine is sophisticated. getWorkload(), capacityPct(), assessTaskRisk(), and suggestReassignment() are genuinely useful calculations. This is the core IP of the product and it's well-implemented.

Debounced auto-save to Supabase is elegant. Rather than saving on every keystroke or requiring manual saves, the 1.5-2s debounce pattern keeps the DB in sync transparently. Keep it exactly as-is.

Slack integration with typed payloads is production-ready. buildTaskAssignedPayload and buildTaskDelayedPayload are well-structured. The toast confirmation is a good UX touch. This is shippable today.

The Crisis Navigator concept is unique. Playbooks + comms templates + scope/timeline/budget trade-off sliders is a genuinely differentiated feature. Once the auth layer is fixed, this alone is worth the whole tool.
